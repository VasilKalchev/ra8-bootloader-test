    Firmware updates over USB DFU with MCUboot on the EK-RA8M2

    The running application receives the new image over the board's USB Full Speed port (J11) with the standard USB DFU protocol and writes it into MCUboot's secondary slot. After a reset MCUboot copies it over the primary slot and starts it. On the PC you only need dfu-util; no debugger is involved after the first install.

      2Board setup and LEDs

      1. Jumpers in the default positions (Part 1, §4). J16 on pins 2-3 for normal boot.
      2. Two USB cables to the PC, both data cables: J10 (DEBUG1, power and J-Link) and J11 (USB Full Speed, the DFU port).
      3. The app drives P500 low at start-up. On the EK-RA8M2 this routes J11 as a USB device port (user's manual 5.4.1).

      Check the TrustZone boundary once. The projects are flat (no TrustZone), so the bootloader and both slots must sit in the Secure area. A board that was last programmed with a TrustZone project keeps that project's boundary. On your board an earlier, hand-flashed TrustZone firmware had left only the first 96 KB of MRAM secure. MCUboot and J-Link then could not reach anything above 0x0201_8000.

      To read or reset it: put J16 on pins 1-2, connect J11, press RESET, then run the script (needs pyserial, §3). Put J16 back on 2-3 and press RESET. This uses the ROM boot firmware commands from R01AN8050 (6.13, 6.14). Your board is already set to all secure, so you do not need to do this again.

      5The DFU application, step by step

      ra8m2_app_*/src/dfu_thread_entry.c, dfu_descriptors.c

      Descriptors: always in DFU mode

      The device only ever shows one interface: class 0xFE, subclass 0x01 (DFU), protocol 0x02 (DFU mode), named "MCUboot secondary slot". There is no runtime mode and no detach step, so dfu-util -a 0 -D file starts writing right away.

      FieldValueNote
      VID:PID1209:0001pid.codes test ID, for development only
      bcdDevice0x0100 / 0x0200Shows which app runs: dfu-util -l prints ver=0100 or ver=0200
      bmAttributes0x01bitCanDnload only. No bitWillDetach, see below.
      wTransferSize256USBX's control transfer limit (UX_SLAVE_REQUEST_CONTROL_MAX_LENGTH)
      bcdDFUVersion1.1

      Writing a block

      USBX calls the write callback once per 256-byte block. MRAM is written in place and needs no erase step, so each block goes straight to its address in the secondary slot:

      uint32_t offset = block_number * DFU_TRANSFER_SIZE;
if (offset + length > DFU_SLOT_SIZE) { g_download_error = true; return UX_ERROR; }

FSP_CRITICAL_SECTION_ENTER;   /* interrupts off while MRAM is in program mode */
err = R_MRAM_Write(&g_mram0_ctrl, (uint32_t) data_pointer, DFU_SLOT_START + offset, length);
FSP_CRITICAL_SECTION_EXIT;

      USBX's DFU class has no handlers for the dfuDNBUSY and dfuMANIFEST states, so the write has to finish inside the callback. MRAM is fast enough for that at 256 bytes per block.

      Finishing the download

      1. After the last (empty) DNLOAD request, USBX sends END_DOWNLOAD. The app notes that the download is done.
      2. At the next GETSTATUS it checks the first word of the slot for the MCUboot image magic 0x96F3B83D. If it is missing, the device reports an error and stays on the current firmware.
      3. If it is there, the main loop waits 1.5 s, turns LED2 off and calls NVIC_SystemReset().

      Why no bitWillDetach, and why the delay. The first version set bitWillDetach and rebooted about 2 ms after the final status. At that moment dfu-util was issuing its own USB reset to the device. The device vanished in the middle of it, and the PC's xHCI controller (0000:02:00.0) hung: dfu-util stuck in state D, the controller could not be unbound, only a PC reboot helped. Without bitWillDetach, dfu-util resets the device while it is still on the bus, and the app reboots only after that. With this fix both directions ran cleanly.

      scripts\flash_jlink.ps1 sends the same J-Link commands as the Linux script to JLink.exe.       scripts/flash_jlink.sh          # bootloader + slow app
scripts/flash_jlink.sh fast     # bootloader + fast app

      Expected: Verify successful., then the board resets on its own, LED3 flashes and LED1 starts blinking. lsusb shows 1209:0001 next to the J-Link (1366:1024).

      What the script does, and why

      • Halts without a reset. J-Link V9.86's built-in RA8 reset fails on this board ("SYSRESETREQ has confused core", then "Failed to select AP0x00000001", and the debug port stays offline until a power cycle). scripts/ra8m2_halt_only_reset.JLinkScript replaces only ResetTarget() with a plain halt.
      • Quiets the CPU (SysTick off, all NVIC interrupts disabled and cleared, PRIMASK set) so the old firmware cannot jump into MRAM while it is rewritten.
      • Writes 0xFF over all of MRAM first. MRAM that was never written reads back as an ECC error, which is a bus fault. MCUboot reads the secondary slot header at every boot, so that slot must hold real data (0xFF = empty) before the first boot. J-Link's erase on MRAM writes nothing, so the script programs the area instead.
      • Loads ra8m2_mcuboot.hex and the signed app at 0x0201_0000, then runs verifybin. loadbin only accepts a .bin extension, so the script copies .bin.signed to a temporary .bin.
      • Resets through AIRCR (SYSRESETREQ) after clearing DEMCR, so the MCU starts MCUboot without the debugger holding it.

      What happens if the download stops halfway

      The signed image is padded to the full slot size (--confirm), so the MCUboot trailer that marks "upgrade pending" sits in the last block. A download that is cut off never writes it. At the next reset MCUboot finds no pending upgrade and keeps running the current firmware, which still has DFU, so you simply send the image again. A power cut during MCUboot's own copy has not been tested. The secondary slot still marks the upgrade as pending until the copy is finished, so MCUboot should start the copy again at the next boot. If it cannot, Validate Primary Image refuses the half-written slot, LED3 blinks fast, and you reflash over J-Link.

      10Limits, and the way to a product

      This setup proves the update path. It is deliberately open, and these are the gaps to close before anyone else gets a board:

      • No signature. MCUboot only checks a SHA-256 hash, so any correctly formatted image is accepted. Switch the bootloader to ECDSA P-256 with your own key (Part 1, §7.3), and keep the private key off the build machine. See Crypto for secure boot.
      • Downgrades are allowed. Turn Downgrade Prevention on once versions only go up.
      • Test VID:PID. 1209:0001 is for development. A product needs its own ID.
      • Overwrite Only. The old image is gone once the copy starts, so a new image that boots but misbehaves cannot be rolled back. Swap mode keeps the old image until the new one confirms itself, at the cost of slower updates (see Firmware updates on the RA8M2).
      • Always in DFU mode. A real product would show its normal USB function and switch to DFU on a DFU_DETACH request or a button.
      • One core. CPU1 is not used. Updating two images over DFU would need a second alternate setting or a combined image.
      • Not hardened. The bootloader keeps the J-Link port open and the lifecycle state unchanged, which is right for learning (Part 1, §10).
